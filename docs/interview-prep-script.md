# 视记 VideoNote 项目面试文稿

## 1 分钟项目介绍

面试官您好，我这个项目叫“视记 VideoNote”，它是一个面向视频学习场景的 AI 知识管理平台。

用户可以粘贴 B 站、抖音、小红书等视频链接，系统会自动获取视频信息和字幕。如果视频有 CC 字幕，就直接解析字幕；如果没有字幕，会走语音转写回退流程。拿到文本后，系统会调用大模型生成结构化摘要、关键知识点、思维导图，并支持基于视频内容继续对话提问。用户还可以把视频保存到笔记本，做知识检索、标签管理、UP 主内容分析，以及公开视频或整个笔记本。

从技术上讲，这是一个 Next.js App Router 的全栈项目，前端用 React 19、Ant Design、Tailwind CSS，后端用 Next API Routes，数据库是 PostgreSQL + Prisma，登录用 NextAuth，AI 调用基于 Vercel AI SDK 和 OpenAI-compatible 模型接口，部署用 Docker、本地打包、服务器 PM2/Nginx。

我在这个项目里主要关注三件事：第一是复杂 AI 工作流的端到端产品化；第二是前端复杂页面的交互和状态管理；第三是全栈工程能力，包括数据库建模、API 设计、SEO、部署和线上稳定性。

## 项目整体架构

这个项目可以分成五层：

第一层是前端页面层。主要包括首页、分析页、笔记本页、公开分享页、知识搜索页、UP 主分析页和登录/管理页面。首页负责输入链接，分析页负责展示视频摘要、思维导图、对话和保存操作，笔记本页负责组织多个视频知识。

第二层是 API 层。Next.js 的 `app/api` 下封装了视频信息获取、字幕获取、转写、摘要、对话、知识抽取、知识搜索、笔记本管理、标签、公开分享和用户认证等接口。

第三层是业务服务层。比如 `lib/bilibili.ts` 负责 B 站 API、WBI 签名和字幕解析；`lib/qwen.ts` 和 `lib/llm.ts` 负责模型配置；`lib/share.ts` 负责公开分享链接；`lib/seo.ts` 负责 SEO 元数据；`lib/videocaptioner.ts` 负责无字幕视频的语音转写回退。

第四层是数据层。使用 PostgreSQL 和 Prisma，核心模型包括 User、Video、Notebook、NotebookVideo、KnowledgePoint、Embedding、UPProfile、VideoTag、ChatMessage、SharePage 等。

第五层是部署和运维层。本地先 Docker 打包，再部署到服务器；线上用 PM2 管理 Node 进程，Nginx 做反向代理，并对长耗时转写接口配置超时和流式响应支持。

## 核心业务流程

用户从首页粘贴视频链接后，前端先调用 `/api/video-info`，后端解析平台链接，获取视频标题、封面、作者、时长、BVID/CID 等元信息。

进入分析页后，会先调用 `/api/subtitle` 获取字幕。如果能拿到 CC 字幕，就直接把字幕转换成统一的结构；如果没有字幕，就调用 `/api/transcribe`，下载音频或视频后走语音识别，最后统一转换成字幕文本。

拿到字幕文本后，前端调用 `/api/summarize`，后端通过 AI SDK 的流式接口生成摘要。前端用 ReadableStream 分块读取，边生成边渲染，用户不用等完整结果返回。

摘要完成后，系统可以进一步把视频保存到数据库，抽取知识点，保存到笔记本；用户也可以继续对视频内容提问，接口是 `/api/chat`。对话时会把字幕和上下文作为模型输入，让回答尽量基于视频原文，不脱离材料乱答。

## 前端亮点

前端部分我重点做了几个能力。

第一是复杂分析页的状态编排。分析页不是简单表单，它有视频信息、字幕状态、AI 摘要流、对话流、思维导图、保存笔记本、标签、模板导出等多个状态。我把流程拆成“获取信息、获取字幕、转写回退、生成摘要、保存和二次交互”几个阶段，每个阶段都有明确的 loading、error 和 success 状态。

第二是流式渲染体验。AI 摘要和对话都是流式返回，前端逐 chunk 读取并更新页面。为了避免高频 setState 导致页面卡顿，摘要渲染做了节流更新，Markdown 渲染也做了样式统一。

第三是信息架构。分析页采用左侧视频/列表，右侧内容详情的结构；公开笔记本分享页也调整成类似分析页的双栏布局，避免内容过长导致用户只能一直滚动。

第四是主题和视觉系统。项目支持明暗主题，使用 CSS 变量统一颜色、边框、卡片和背景。最近还处理过一个首屏样式闪烁问题，把导航和首页首屏关键样式从 `styled-jsx` 移到 `globals.css`，让首屏 CSS 直接阻塞加载，减少 FOUC。

第五是 SEO 友好页面。首页、功能页、FAQ、公开分享页都有 metadata、canonical、Open Graph、Twitter Card、robots、sitemap 和 JSON-LD 结构化数据支持。这对一个需要公开分享和搜索收录的工具很重要。

## 全栈能力体现

这个项目不是纯前端 Demo，而是一个完整全栈系统。

认证方面，用 NextAuth 做登录态管理，同时支持邮箱注册、邮箱验证、B 站扫码登录状态检查等能力。用户数据和视频数据都按 userId 做隔离。

数据库方面，我用 Prisma 建模。Video 表保存视频基础信息、字幕文本、摘要和知识抽取状态；Notebook 和 NotebookVideo 处理笔记本和视频的多对多关系；KnowledgePoint 保存主题、关键点、概念、问答等结构化知识；SharePage 用统一模型支持公开视频和公开笔记本两种分享目标。

API 方面，接口分层比较明确。视频分析相关接口负责数据获取和 AI 生成，笔记本接口负责组织内容，分享接口负责公开访问权限，搜索接口负责全局检索和字幕检索，管理接口负责后台用户管理。

AI 方面，我没有直接把 prompt 写死在页面里，而是把模型配置、prompt、知识抽取 schema 和模板输出做了模块化。这样后续切模型、改 prompt、加导出格式都比较容易。

部署方面，项目支持本地 Docker 打包后部署到服务器，线上用 Nginx 反代和 PM2 管理。因为视频转写属于重任务，我还加了并发限制、文件大小限制、下载和转写超时，避免服务器被大视频拖垮。

## 可以重点讲的技术难点

### 难点一：B 站字幕接口和 WBI 签名

B 站部分接口需要 WBI 签名，不是简单请求就能拿数据。处理流程是先请求 nav 接口获取 `img_key` 和 `sub_key`，再根据固定索引表生成 mixin key，然后把参数排序、过滤特殊字符、加时间戳，最后 MD5 生成 `w_rid`。

这个难点体现的是我对第三方平台接口逆向规则、签名参数和稳定性处理的理解。

### 难点二：无字幕视频的回退机制

不是所有视频都有 CC 字幕，所以我设计了字幕优先、转写兜底的流程。有字幕就快路径处理；没字幕就调用转写服务，转成 SRT 后再解析成统一的 SubtitleItem 结构。这样上层摘要、对话、保存逻辑不用关心字幕来源。

这个难点体现的是容错设计和数据结构抽象。

### 难点三：AI 流式输出与前端体验

AI 摘要和对话如果等完整结果返回，体验会很差。所以我用 AI SDK 的 streamText，后端直接返回 text stream，前端逐块读取。渲染时要处理 Markdown、节流更新、loading 状态、异常中断和最后结果落库。

这个难点体现的是流式接口、异步状态管理和用户体验优化。

### 难点四：从单视频分析扩展到知识库

最开始这个项目只是视频摘要工具，后来扩展成知识管理平台。扩展时我加了 Notebook、KnowledgePoint、Embedding、VideoTag、ChatMessage、SharePage 等模型，让视频可以被组织、检索、对话和公开分享。

这里体现的是产品演进中的数据建模能力，不是简单把功能堆在页面上。

### 难点五：SEO 和公开分享

公开分享页如果只有客户端渲染，对搜索引擎和社交预览都不好。所以分享页做了服务端 metadata、canonical、OG 图、结构化数据和 sitemap。首页也补充了功能说明、FAQ、公开笔记入口和法律/关于页面。

这个难点体现的是我对 Next.js SSR、SEO 和内容可发现性的理解。

## 项目中的一次真实问题复盘

最近我处理过一个首页首屏样式加载问题。本地和服务器打开首页时，会先出现 0.5 秒无样式页面，然后样式恢复。

排查后发现，导航和首页主体样式原来写在 `styled-jsx` 中。SSR HTML 已经先返回了结构，但这些组件样式依赖客户端 JS 注入，所以首屏会先裸奔。

解决方案是把首屏关键样式移到 `src/app/globals.css`，因为它由根布局直接加载，会作为首屏 CSS 参与阻塞渲染。这样导航、首页 hero、搜索框、功能区都不再依赖 hydration 后注入样式。

中间还遇到一个本地 dev 缓存问题：代码已经移到全局 CSS，但 `next dev` 仍返回 `.next/dev` 的旧 CSS，导致页面完全无样式。最后通过清理 `.next/dev` 并重启 dev server 解决。

这件事能说明我处理问题时不是只看表象，而是会从 HTML、CSS chunk、构建产物和浏览器实际加载链路去定位。

## 高频问答准备

### Q1：这个项目解决了什么问题？

它解决的是长视频学习效率低的问题。很多技术视频、课程、访谈内容有价值，但用户很难快速定位重点，也很难沉淀成可复用知识。这个项目把视频转换成摘要、知识点、思维导图和可搜索笔记，让视频内容进入个人知识库。

### Q2：为什么用 Next.js 做全栈？

因为这个项目既需要 SEO 和公开分享，也需要后端 API、认证、数据库和 AI 流式接口。Next.js App Router 可以把页面、metadata、API Routes 和 SSR 放在同一个工程里，开发效率高，也方便部署。

### Q3：为什么不用纯客户端渲染？

公开分享页、首页、FAQ、功能页都需要被搜索引擎收录和社交平台预览。纯客户端渲染不利于 SEO，也不利于首屏性能。Next.js 的服务端渲染和 metadata API 更适合这个场景。

### Q4：AI 输出如何保证不乱答？

第一，摘要和对话都把字幕文本作为主要上下文；第二，prompt 中明确要求基于视频内容回答，不确定就说明无法从视频中确认；第三，知识点抽取使用结构化 schema，降低输出格式不稳定的问题。

### Q5：视频没有字幕怎么办？

系统会先走 CC 字幕获取，如果没有字幕，会进入转写回退流程。转写完成后统一解析成 SubtitleItem，因此后续 AI 摘要、对话、保存逻辑不需要区分字幕来源。

### Q6：项目里你最有技术含量的部分是什么？

我会选三个：B 站 WBI 签名和字幕获取、AI 流式输出的前后端联动、从单视频分析扩展到知识库的数据建模。这三个分别对应外部接口处理、用户体验和系统架构。

### Q7：如何处理大视频导致服务器压力？

我做了几个限制：转写并发限制、音频文件大小限制、下载超时、转写超时、临时文件清理、PM2 内存重启阈值。这样可以避免多个大视频同时把 CPU、内存或磁盘打满。

### Q8：数据库为什么这么设计？

Video 是视频内容的中心表，保存字幕、摘要和元信息。Notebook 和 NotebookVideo 是多对多关系，让一个视频可以进入不同笔记本。KnowledgePoint 从视频中抽取结构化知识。SharePage 用 targetType 和 targetId 统一支持公开视频和公开笔记本，避免为不同分享类型重复建表。

### Q9：搜索是怎么做的？

项目支持字幕搜索、全局搜索和知识点检索。基础搜索可以基于数据库文本字段；知识点层面预留了 Embedding 模型和 pgvector 字段，后续可以做语义搜索。

### Q10：你做过哪些性能优化？

前端上做了 AI 流式渲染、Markdown 更新节流、首屏关键 CSS 全局加载，避免 FOUC。后端上对转写任务做并发、大小和超时控制。SEO 上通过服务端 metadata 和结构化数据提升公开页面可发现性。

### Q11：如果继续优化，你会怎么做？

我会优先做四件事：第一，把转写任务改成队列，避免 HTTP 长请求；第二，完善 pgvector 语义搜索；第三，增加 Playwright 端到端测试覆盖分析和分享流程；第四，继续优化公开内容的 SEO 和站点结构。

### Q12：这个项目有什么不足？

目前转写仍然偏重，最好拆成异步任务队列；AI 生成内容还可以增加引用定位，让摘要和原字幕时间戳更强绑定；测试体系还可以补充更多 E2E 场景；公开分享页也可以继续做缓存和增量更新。

如果面试官让我完整介绍一个项目，我会这样说：

我想介绍的是我做的一个全栈 AI 视频知识管理项目，叫视记 VideoNote。

它的核心场景是把长视频变成可检索、可对话、可沉淀的知识笔记。用户粘贴一个 B 站、抖音或小红书视频链接，系统会获取视频信息和字幕。如果视频本身有 CC 字幕，就直接解析；如果没有字幕，就走语音转写回退。拿到文本后，会调用大模型生成摘要、关键知识点和思维导图，用户还可以继续基于视频内容提问，并把结果保存到笔记本。

技术栈上，项目使用 Next.js App Router 和 React 19，UI 使用 Ant Design 和 Tailwind CSS，后端 API 直接用 Next API Routes。数据层是 PostgreSQL + Prisma，认证用 NextAuth，AI 部分使用 Vercel AI SDK 接 OpenAI-compatible 模型接口。部署上是本地 Docker 打包，然后到服务器用 PM2 和 Nginx 运行。

我觉得这个项目最有价值的地方有三个。

第一是完整的 AI 工作流。它不是只调一次模型，而是从链接解析、字幕获取、无字幕转写、摘要生成、知识抽取、对话问答到保存分享形成闭环。

第二是工程复杂度比较完整。它有用户系统、数据库建模、文件处理、长耗时任务、流式响应、公开分享、SEO 和线上部署，不是一个纯前端页面。

第三是我在里面解决了一些真实问题。比如 B 站接口需要 WBI 签名；无字幕视频需要转写兜底；AI 输出要做流式渲染；公开页面要做 SEO；最近还修复了首页首屏样式闪烁的问题，把关键样式从 `styled-jsx` 移到全局 CSS，避免等待 hydration 后才注入样式。

如果继续迭代，我会把转写改成异步任务队列，引入更完善的向量检索，并补充 E2E 测试，让它更接近生产级 SaaS 工具。
