# Bilibili Subtitle Analyzer 项目讲解文稿

适用场景：项目答辩、技术评审、架构汇报、产品技术介绍。

建议讲解时长：8-12 分钟。

---

## 第 1 页：封面

### 讲解重点

- 先定义项目是什么。
- 强调这不是单纯的字幕工具，而是视频内容知识化工具。
- 点出本次汇报会覆盖架构、数据库表、ER 图和后续演进。

### 口播稿

大家好，这次我介绍的是 Bilibili Subtitle Analyzer，也可以理解为一个 VideoNote 类型的视频内容分析系统。

这个项目的核心目标是：用户输入一个视频链接，系统自动解析视频信息，获取字幕；如果没有字幕，就走音频转写；拿到文本之后，再通过大模型生成摘要、支持对话问答，并把视频、字幕、摘要、知识点、笔记和标签沉淀到数据库里。

所以它不是一个简单的“字幕提取器”，而是一个从视频链接到结构化知识资产的完整闭环。接下来我会从总体架构、核心链路、模块边界、部署方式、数据库表图和 ER 图几个角度来展开。

---

## 第 2 页：项目总体架构图

### 讲解重点

- 系统是 Next.js BFF 型全栈架构。
- 前端、API、领域服务、外部平台、AI、数据库都在同一应用内编排。
- videos 和 users 是业务主轴。

### 口播稿

这一页是项目的总体架构。

最左边是用户侧，主要包括首页、分析页、笔记本、搜索页和 UP 主分析页。用户的主要动作是输入视频链接、查看摘要、和视频内容对话、管理笔记和标签。

中间是 Next.js 的 BFF 层，也就是 API Routes。这个层是整个系统的调度中心，它负责接收前端请求，并把请求分发给不同的领域模块，比如视频信息解析、字幕获取、音频转写、AI 摘要、聊天、搜索和数据保存。

再往右是领域服务层。这里有三个关键能力：第一是多平台适配，支持 B 站、抖音和小红书；第二是字幕链路，优先拿平台 CC 字幕，没有字幕时走音频下载和 VideoCaptioner 转写；第三是 AI 链路，通过 Vercel AI SDK 和多模型供应商做流式摘要与对话。

最右侧是外部依赖和持久化。外部依赖包括 B 站 API、抖音和小红书页面、LLM Provider、文件系统临时目录；持久化主要是 PostgreSQL，通过 Prisma 管理用户、视频、知识点、笔记本、标签、聊天记录等数据。

总结一下，这个系统是一个典型的 Next.js BFF 全栈架构：前端负责交互，API Routes 负责业务编排，领域模块负责具体能力，数据库负责长期知识沉淀。

## 第 3 页：架构解析：BFF 是系统的中枢

### 讲解重点

- BFF 不只是转发接口。
- 服务端承担密钥保护、跨域规避、平台适配和数据落库。
- 单体架构适合当前阶段快速迭代。

### 口播稿

这一页重点讲 BFF 层。

项目选择了 Next.js App Router 和 API Routes，因此前端页面和服务端接口都在同一个代码库里。这个设计的好处是开发和部署都比较轻量，同时也能把敏感逻辑留在服务端。

例如 B 站的 SESSDATA、DashScope API Key、数据库连接字符串这些敏感信息，都不会暴露到浏览器。前端只调用自己的 `/api/video-info`、`/api/subtitle`、`/api/summarize` 等接口，由服务端再去请求外部平台或大模型。

BFF 层还有一个很重要的职责是统一编排业务流程。比如用户输入一个链接以后，它不需要关心这是 B 站、抖音还是小红书，也不需要关心有没有 CC 字幕。BFF 会根据平台自动走不同的解析路径，并在字幕缺失时自动进入转写降级链路。

所以这里的 BFF 不是简单代理，而是整个系统的业务中枢。它把前端体验、平台能力、AI 能力和数据库能力组合成一个完整产品。

## 第 4 页：核心业务链路：从链接到知识资产

### 讲解重点

- 讲清楚主流程的 6 步。
- 强调字幕优先、转写兜底。
- 强调同一视频内容可复用，用户行为个性化隔离。

### 口播稿

这一页是核心业务链路。

第一步，用户输入视频链接。这里不仅支持标准 URL，也支持从 App 里复制出来的分享文案，因为实际用户经常复制的是一整段文字。

第二步，系统进行平台识别和 ID 提取。`platform.ts` 会识别输入属于 B 站、抖音还是小红书，然后解析出对应的视频 ID，比如 B 站的 bvid、抖音的 aweme_id、小红书的 noteId。

第三步，获取视频元信息。系统会拿到标题、封面、作者、时长、CID、分 P 信息等，为后续分析页展示和字幕请求做准备。

第四步，进入字幕链路。系统优先请求平台已有的 CC 字幕，因为这是最快、成本最低、准确率最高的方式。如果视频没有 CC 字幕，就进入音频下载和 VideoCaptioner 转写流程，最后把 SRT 解析成统一的字幕结构。

第五步，进入 AI 生成。系统会基于字幕文本生成摘要，支持用户继续围绕视频内容提问，同时也可以抽取结构化知识点。

第六步，数据沉淀。视频、字幕、摘要、知识点会保存到 videos 和 knowledge_points 等表里；用户自己的历史、标签、笔记、聊天记录则通过带 user_id 的表来隔离。

这里有一个关键设计：视频内容资产和用户个性化数据是分开的。同一个视频不用重复抓取和转写，但不同用户可以有自己的笔记、标签和对话历史。

## 第 5 页：模块边界：平台、字幕、AI、知识四条主干

### 讲解重点

- 平台接入：多平台统一入口。
- 字幕转写：CC 字幕与转写兜底。
- AI 编排：多模型供应商和流式输出。
- 知识产品：历史、笔记本、标签、搜索。

### 口播稿

这一页从代码结构角度看模块边界。

第一条主干是平台接入。`src/lib/platform.ts` 是统一入口，负责识别平台和提取视频 ID；`bilibili.ts` 处理 B 站 API、WBI 签名和字幕接口；`douyin.ts` 和 `xiaohongshu.ts` 负责短链解析、页面解析和视频元信息提取。

第二条主干是字幕和转写。`/api/subtitle` 负责获取 CC 字幕；`/api/transcribe` 负责在没有字幕时触发音频转写；`videocaptioner.ts` 封装了 VideoCaptioner CLI、SRT 解析和临时文件清理。

第三条主干是 AI 编排。`llm.ts` 把不同模型供应商统一起来，支持 DashScope、DeepSeek、OpenAI、Kimi、GLM、Anthropic 和自定义 OpenAI Compatible Provider。`summarize`、`chat`、`knowledge/extract` 这些 API 都基于这个模型抽象来工作。

第四条主干是知识产品能力。`videos`、`notebooks`、`search`、`tags` 相关 API 负责把一次性分析结果变成可管理、可搜索、可复用的学习资料。

这个模块拆分的好处是后续扩展比较自然。比如新增一个视频平台，主要改 platform adapter；新增一个模型供应商，主要改 llm 配置；新增知识组织能力，主要围绕数据库和 API 扩展。

## 第 6 页：部署架构：小内存服务器的 standalone 发布

### 讲解重点

- 当前服务器资源有限，不能在线上直接 npm install/build。
- 本地 Docker 构建 linux/amd64 standalone。
- 服务器只负责解压、切 current、PM2 启动。

### 口播稿

这一页是部署架构。

当前线上服务器是阿里云 ECS，资源比较小，只有 2 核 2G。所以项目没有采用“服务器上直接 npm install、npm run build”的方式，因为 Next.js 构建、Prisma 生成、依赖安装会吃很多内存，很容易触发 swap 或卡死。

现在推荐的部署方式是 standalone 发布。

第一步在本地或 CI 里用 Docker 构建，指定 linux/amd64，保证构建产物和服务器架构一致。构建完成后拿到 `.next/standalone`、`.next/static` 和 public 静态资源。

第二步把产物打包成 tar.gz 上传到服务器的 uploads 目录，每个 commit 对应一个 release 目录。

第三步服务器解压 release，把生产环境的 `.env`、`.env.local` 和必要 data 文件复制进去，然后把 current 软链切到新的 release。

第四步用 PM2 启动 `start-server.js`，Nginx 再把公网请求反向代理到本机 3000 端口。

这个方案的核心是：构建压力放在本地或 CI，线上机器只运行已经构建好的 Node 服务，适合低内存服务器。

## 第 7 页：数据库表图：按职责域分组

### 讲解重点

- 一共 13 张业务表。
- 按认证用户、视频核心、笔记本组织、知识检索、个人化标注分组。
- users 与 videos 是两个主轴。

### 口播稿

这一页是数据库表图。

项目的数据库表可以分成五组。

第一组是认证与用户，包括 `users` 和 `email_verification_tokens`。`users` 保存用户基础信息、密码哈希和邮箱验证状态；`email_verification_tokens` 用于邮箱验证流程。

第二组是视频核心，包括 `videos`、`user_videos` 和 `up_profiles`。其中 `videos` 是内容资产中心，保存视频标题、封面、CID、字幕全文、摘要和知识抽取状态。`user_videos` 用来记录某个用户分析或收藏过哪些视频。`up_profiles` 保存 UP 主档案。

第三组是笔记本组织，包括 `notebooks` 和 `notebook_videos`。用户可以把视频加入不同笔记本，并记录顺序和备注。

第四组是知识与检索，包括 `knowledge_points`、`embeddings` 和 `chat_messages`。知识点表保存从视频里抽取出的主题、关键点、概念等结构化内容；embedding 表保存向量，方便后续语义检索；聊天记录表保存用户围绕视频产生的对话。

第五组是个人化标注，包括 `video_timestamp_notes`、`video_tags` 和 `video_tag_relations`。这些表都和 user_id 相关，用来保存用户自己的时间戳笔记、标签和标签关系。

整体来看，数据库围绕两个主轴展开：一个是 users，负责权限和个性化；一个是 videos，负责内容资产和知识沉淀。

## 第 8 页：ER 图：实体关系与基数

### 讲解重点

- users 与 videos 通过 user_videos 形成用户历史关系。
- notebooks 与 videos 通过 notebook_videos 形成多对多。
- video_tags 与 videos 通过 video_tag_relations 形成用户级标签关系。
- knowledge_points 与 embeddings 是 1:1。

### 口播稿

这一页是 ER 图。

最核心的实体是 users 和 videos。

users 到 user_videos 是一对多，videos 到 user_videos 也是一对多，所以 user_videos 本质上承担了用户和视频之间的多对多关系。它能记录某个用户看过或分析过哪些视频，同时同一个视频也可以被多个用户复用。

notebooks 和 videos 之间通过 notebook_videos 连接，这也是多对多关系。一个笔记本可以包含多个视频，一个视频也可以出现在多个笔记本里。

knowledge_points 属于 videos，是视频内容的结构化产物；embeddings 和 knowledge_points 是一对一关系，因为每个知识点可以对应一个向量表示。

标签这块，video_tags 是用户创建的标签，video_tag_relations 把 user、video 和 tag 三者关联起来。这样可以保证标签是用户级别的，不同用户给同一个视频打的标签不会互相影响。

chat_messages 同时关联 user 和 video，表示某个用户围绕某个视频产生的对话记录。

所以这张 ER 图体现了一个核心原则：视频内容资产尽量共享，用户行为数据保持隔离。

## 第 9 页：数据模型解读：为什么这样拆表

### 讲解重点

- 内容资产中心：videos。
- 用户隔离层：user_id 相关表。
- 知识检索层：knowledge_points + embeddings。
- 组织层：notebooks。

### 口播稿

这一页解释为什么数据库要这样拆。

首先，videos 是内容资产中心。一个视频的字幕、摘要、知识点抽取状态都保存在这里。这样同一个视频被多个用户分析时，不需要重复抓取字幕和重复生成基础信息。

其次，用户个性化行为单独拆出来。比如用户历史、时间戳笔记、标签、聊天记录，都带 user_id。这样一方面保护用户之间的数据隔离，另一方面也让公共视频资产可以复用。

第三，知识检索层单独拆成 knowledge_points 和 embeddings。knowledge_points 保存可读的结构化知识，embeddings 保存向量数据。这样未来要做语义搜索、相似知识推荐、跨视频知识检索时，数据结构已经有扩展空间。

第四，notebooks 是组织层。它不是视频本身的一部分，而是用户学习和整理视频的方式，所以通过 notebook_videos 做关联，而不是直接把 notebook_id 放在 videos 上。

这个拆表方式的好处是职责清晰：公共资产、用户行为、知识检索、内容组织各自独立，但又通过外键关系连接起来。

## 第 10 页：后续架构关注点

### 讲解重点

- 长任务要异步化。
- 抓取能力需要更强的可观测性。
- 迁移与发布流程要分离。
- 知识检索可以继续增强。

### 口播稿

最后讲一下后续架构关注点。

第一个是转写任务异步化。目前音频下载和转写仍然比较接近请求链路，视频一大或者并发一高，就容易占用服务器资源。后续更理想的方式是引入任务队列或任务表，让转写、知识抽取这些长任务异步执行，并支持进度查询、失败重试和恢复。

第二个是抓取依赖的稳定性。抖音和小红书解析依赖页面结构、短链跳转或 XHR 数据，这类能力天然会受到反爬和页面变化影响。后续需要更完善的日志、降级策略和错误分类。

第三个是迁移与发布分离。当前 standalone 发布已经解决了线上构建压力，但数据库 migration 最好也不要依赖线上源码目录临时安装依赖。更好的方式是用 CI 执行 migration，或者准备一个一次性迁移镜像。

第四个是知识检索增强。现在已经有 knowledge_points 和 embeddings 的基础，后续可以补充语义召回、重排、引用片段、权限过滤和跨视频知识网络。

整体总结一下：当前架构非常适合快速迭代和单机部署；当使用量上来以后，优先要把长任务、抓取、知识抽取从同步请求链路中拆出来，变成可观测、可恢复、可扩展的后台任务。

## 30 秒极简版总结

如果时间很短，可以这样讲：

这个项目是一个基于 Next.js 16 的视频内容知识化系统。用户输入 B 站、抖音或小红书链接后，系统通过 BFF 层统一解析平台、获取视频元信息、优先读取 CC 字幕，没有字幕时走 VideoCaptioner 转写。拿到字幕后，系统调用多模型 LLM Provider 生成摘要、支持对话和知识点抽取，并通过 Prisma 保存到 PostgreSQL。

架构上，它是一个单体 BFF 全栈应用，优点是部署简单、密钥安全、迭代快；数据模型围绕 users 和 videos 两个主轴展开，公共视频资产复用，用户笔记、标签、聊天记录隔离。线上部署采用本地 Docker 构建 `.next/standalone`，服务器用 PM2 和 Nginx 运行，适配小内存 ECS。

后续最重要的演进方向是把转写、抓取和知识抽取这类长任务异步化，并增强任务可观测性和失败恢复能力。
